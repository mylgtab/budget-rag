# 成本感知检索：预算、级联与评测基线

> 工作草稿（v0.3）。所有数字可用 `make all` 复现。

## 摘要

长文档问答中，检索深度与上下文长度直接决定 token 成本，但并非每个问题都值得深检索。
我们实现了一个预算可调的 RAG 检索层，比较四种策略：固定浅检索、固定深检索、按全局预算路由、
以及按置信度级联升级。在 200 条合成问答上，级联策略在改写题集上取得 0.970 的 Recall@3，
成本为固定深检索的 47%；在原始问句集上与深检索持平，成本为 33%。
我们也报告一个负结果：在词汇重合度高的合成集上，简单 BM25 top-3 已接近饱和，
与深检索的差距落在置信区间内，说明**合成数据不足以区分策略**。

## Abstract

Retrieval depth dominates the token cost of document QA, yet not every question deserves a deep
retrieval pass. We implement a budget-aware retrieval layer and compare four policies: fixed
shallow, fixed deep, global-budget routing, and confidence-based cascading. On 200 synthesized
questions, the cascade reaches 0.970 Recall@3 on a paraphrased split at 47% of the deep-retrieval
cost, and matches deep retrieval on the literal split at 33% of the cost. We also report a negative
result: on lexically overlapping synthetic data, plain BM25 top-3 already saturates, so differences
between policies fall inside the confidence interval — synthetic data cannot separate them.

## 1 问题

RAG 的成本由两部分构成：检索回来的上下文 token，以及生成答案的 token。
固定 top-k 的做法对所有问题一视同仁，简单问题被过度检索，难问题又召回不足。

设单次查询预算为 `B`，我们希望在这个预算内最大化 Recall@k，同时让实际花费尽量靠近 `B` 而不是超过它。

## 2 方法

**2.1 预算三档（`adaptive-budget`）**
按 `B` 划分检索深度：紧预算 `k=1` 纯 BM25；常规 `k=2` BM25；宽裕 `k=5` 混合检索（BM25 与向量归一化加权）。
问题长度、实体数、是否含比较类词汇决定是否额外加码。

**2.2 置信度级联（`cascade-conf`）**
先做 BM25 `k=2`，计算 top1 与 top2 的相对差距 `(s1-s2)/s1`；
若差距小于阈值（默认 0.25），认为检索拿不准，升级为混合检索 `k=5`；否则直接返回。
这样成本随问题难度自动分摊，而不是随全局预算。

**2.3 成本模型**
按 1k token 计价：BM25 档 0.0005 元，混合档 0.002 元。
上下文 token 按字数/1.5 粗估。该模型是简化假设，见第 6 节。

**2.4 与已有工作的差异**

- **Adaptive-RAG**（Jeong et al., NAACL 2024）训练一个查询复杂度分类器，把问题分成
  「不检索 / 单步 / 多步」三档再决定检索深度。我们不做训练，用 BM25 分数间隔这种
  零成本信号做门控，目标是同等效果下不引入额外模型。
- **CRAG**（Corrective RAG）用一个轻量评估器给检索结果打「正确/错误/模糊」，
  再触发纠正动作（换检索源、重写查询）。我们的级联与门控在思路上相似，
  但纠正动作限定为「改写查询 + 混合检索」，且评估器是分数间隔而非微调模型。
- **Cost-Aware RAG**（Wu et al., 2026）给证据分配「访问成本档位」，
  在显式预算下选择证据，并指出**静态选择器很脆、预算变大不必然变好**。
  这与我们观察一致（合成集上 naive 已饱和、预算升到 800 只换来 8% 成本差而召回持平）。
  区别在于：他们研究「证据要花钱买」，我们研究「上下文 token 要花钱占」。

## 3 实验设置

- 语料：10 篇技术笔记（操作系统、网络、数据库、Python、Git、Docker、算法、测试、HTTP 缓存、RAG），共 200 条事实句
- 评测集 A（literal）：模型从原文抽问，答案逐字来自原文，200 条
- 评测集 B（paraphrased）：额外要求问句不出现原文术语，200 条
- 指标：Recall@k（答案句是否进入召回上下文）、EM、F1、每 query 成本、p95 延迟
- 置信区间：对逐条结果做 1000 次自助重采样，取 95% 区间
- 生成模型：DeepSeek-V4.1-Flash；检索与打分为纯 CPU、无外部依赖

## 4 结果

### 4.1 原始问句集（literal, n=200）

| 策略 | Recall@3 (95% CI) | F1 | cost/q (元) |
|---|---|---|---|
| `naive-bm25-k3` | 0.980 [0.960, 0.995] | 0.859 | 0.000291 |
| `fixed-bm25-k1` | 0.911 [0.871, 0.946] | 0.876 | 0.000105 |
| `fixed-hybrid-k5` | 0.980 [0.960, 0.995] | 0.860 | 0.001936 |
| `adaptive-budget` | 0.980 [0.960, 0.995] | 0.860 | 0.001976 |
| `cascade-conf` | 0.980 [0.960, 0.995] | 0.869 | 0.000644 |

### 4.2 改写问句集（paraphrased, n=200）

| 策略 | Recall@3 (95% CI) | F1 | cost/q (元) |
|---|---|---|---|
| `naive-bm25-k3` | 0.965 [0.935, 0.990] | 0.764 | 0.000295 |
| `fixed-bm25-k1` | 0.855 [0.810, 0.900] | 0.753 | 0.000105 |
| `fixed-hybrid-k5` | 0.975 [0.955, 0.995] | 0.757 | 0.001942 |
| `adaptive-budget` | 0.975 [0.955, 0.995] | 0.757 | 0.001995 |
| `cascade-conf` | 0.970 [0.945, 0.990] | 0.761 | 0.000917 |

### 4.3 真实模型作答（202 条，账单 token）

前两节用离线抽取作答（零成本），只衡量检索。本节让模型读上下文生成答案，
token 数直接取自 API 返回的 `usage`，成本按 2 元/百万输入、8 元/百万输出计算。

| 版本 | 改动 | EM | Contain | F1 | 输入/输出 token | cost/q |
|---|---|---|---|---|---|---|
| v1 | 提示词只说「根据资料回答」 | 0.228 | 0.624 | 0.805 | 892.8 / 17.8 | 0.001928 元 |
| v2 | 要求「只输出答案、逐字照抄」+ 前缀清洗 | **0.520** | **0.985** | 0.813 | 957.8 / 11.4 | 0.002007 元 |

**EM 翻倍，Contain 达到 98.5%。** 但要注意：v1 的 EM 低不是答错，而是模型加了
「根据资料[1]，」前缀并改写措辞；Contain 指标（预测与标准答案互相包含）才反映真实质量。
这也说明**单看 EM 会低估系统**，评估指标本身需要被审视。

全套 202 条跑一次约 3 分钟、花 0.4 元。

### 4.4 扩到 500 条（16 篇语料）

| 指标 | 值 |
|---|---|
| Recall@3 | 0.946 |
| EM | 0.614 |
| Contain | 0.920 |
| F1 | 0.776 |
| 输入/输出 token | 971.8 / 11.3 |
| cost/q | 0.002034 元 |
| p95 延迟 | 1205 ms |

失败 40 条，其中 **24 条是检索没召回**、16 条是召回到了却拒答或答错。
针对拒答加了「强制挑最接近一句」的二次兜底，在同一子集上救回 7/40（17.5%）。
结论：当前瓶颈在**检索**，不在生成。

### 4.5 分块粒度：在相同 token 预算下重做

上一轮按 `Recall@k` 比较，句级切块（0.832）输给固定 320 字切块（0.946）。
但 `Recall@k` 衡量的是「召回上下文里是否出现答案句」，**块越大越占便宜**，比较不公平。
改成按 token 预算取块后重测：

| 上下文预算 | fixed 召回 | sentence 召回 |
|---|---|---|
| 80 tok | 0.800（实际 192） | **0.850（实际 90）** |
| 120 tok | 0.808（205） | **0.876（130）** |
| 200 tok | 0.836（253） | **0.892（212）** |
| 300 tok | 0.894（397） | **0.912（314）** |
| 500 tok | 0.918（592） | **0.928（518）** |
| 800 tok | **0.954（892）** | 0.938（824） |

结论：

1. **预算 ≤500 token 时句级切块更好**，同等召回下省 15%–50% 上下文。
2. **句级切块的预算控制更准**：要 80 token 时它只花 90，固定块却花到 192——
   大块的最小粒度就是 320 字，预算再小也压不下去。
3. 预算 >800 时固定块反超：事实级过细，块数多、排序误差累积。

图：`docs/figures/chunk_budget.svg`；复现：`python scripts/chunk_budget.py`

### 4.6 双索引自动选择

据 4.5 的结论，实现 `chunk_mode=auto`：同时建句级与固定块两套索引，
上下文预算 ≤500 token 走句级，否则走固定块；取块按累计 token 停止，而不是按固定 k。

500 条离线评测（无 API 成本）：

| 上下文预算 | 选用索引 | Recall | cost/query |
|---|---|---|---|
| 100 tok | sentence | 0.850 | 0.00025 元 |
| 300 tok | sentence | 0.900 | 0.00065 元 |
| 800 tok | fixed | 0.944 | 0.00181 元 |

相比固定 `k=3`（Recall 0.946、0.00196 元），300 token 档用 **1/3 的成本**拿到 0.900；
预算提到 800 时召回追平而成本仍低 8%。

### 4.7 真模型验证 auto 档（500 条，真实账单）

上一节的 auto 对比是离线指标，本节用真实模型跑完整链路（同一题序，可配对比较）：

| 指标 | 固定 k=3 | auto（300 tok） |
|---|---|---|
| Recall | 0.946 | 0.900 |
| EM | 0.614 | **0.700** |
| Contain | 0.920 | 0.912 |
| F1 | 0.776 | **0.819** |
| 上下文 tokens | 971.8 | **473.6** |
| cost/q | 0.002034 元 | **0.001050 元** |
| p95 延迟 | 1205 ms | 1823 ms |

**配对结果**（同题序 500/500）：Contain 上 auto 更好 22 条、固定更好 26 条、持平 452 条。
差异落在噪声内，但**上下文 token 只有 1/3，成本接近一半**。

EM 与 F1 反而上升，一个合理解释是：上下文变短后，模型更容易逐字命中原文句子，
而不是在多块里拼接改写。这条解释尚未单独验证，列为待办。

### 4.8 查询改写：免费方案失败，付费方案有效

4.4 指出 60% 的失败来自检索没召回，本节解决它。

**零成本方案：伪相关反馈（PRF）。** 用首轮结果里权重最高的词扩查询，纯词法。
结果**更差**：句级索引 −1.6pt、固定块 −19.6pt。原因是对比类问题会被无关高频词带偏（查询漂移）。

**付费方案：模型改写。** 让模型把口语问题改写成 5–10 个检索词，再用「原始 + 改写」扩查询。

| 数据集 | 原始查询 | 模型改写（替换） | 原始+改写（扩） |
|---|---|---|---|
| 500 条（句级 300 tok） | 0.912 | 0.954 | **0.958** |

端到端验证（同 200 题，题序一致）：

| 指标 | auto300 | auto300 + 改写 |
|---|---|---|
| Recall | 0.915 | **0.980** |
| Contain | 0.915 | **0.985** |
| EM | 0.710 | 0.770 |
| F1 | 0.827 | 0.883 |
| cost/q | 0.001049 元 | 0.0011 元（含改写调用） |
| p95 延迟 | 1823 ms | 2970 ms |

逐条配对：Contain 上**改写更好 15 条、基线更好 1 条、持平 184 条**。

代价是一次额外的小调用（约 60 输出 token），换来 +6.5pt 召回；延迟翻倍。
是否开启取决于预算：`RAG_REWRITE=1` 启用，默认关闭。

### 4.9 人工标注校准自动指标（两批各 100 条）

请标注员按 1/2/3 打分（3=完全正确，2=方向对但有缺漏，1=错），与自动指标逐条对照。

**批次 A：抽取式作答（旧链路）**

| 人工 \ 自动 contain | 判对 | 判错 |
|---|---|---|
| 3 分 | 66 | 5 |
| 2 分 | 2 | 4 |
| 1 分 | 1 | 22 |

人工正确率 **77.0%**，自动 contain **69.0%**，EM **60.0%**；
一致率 90.0%，精确率 98.6%，召回率 88.3%。

**批次 B：LLM 作答（auto 300 + 查询改写）**

| 人工 \ 自动 contain | 判对 | 判错 |
|---|---|---|
| 3 分 | 89 | 1 |
| 2 分 | 7 | 1 |
| 1 分 | 1 | 1 |

人工正确率 **98.0%**，自动 contain **97.0%**，EM **81.0%**；
一致率 97.0%，精确率 99.0%，召回率 98.0%。

**两个结论：**

1. **EM 系统性低估**（60% 对 77%、81% 对 98%），不适合作为主指标；
   contain 与人工的一致率在 90%–97%，可以当主指标。
2. **自动指标的偏差方向随答案质量变化**：答案质量低时它偏保守
   （批次 A 漏判 9 条「部分正确」的答案），质量高时几乎与人工重合（批次 B 只差 2 条）。
   因此跨系统比较时，`contain` 的差值应理解为**质量差值的下界**。

**标注者一致性（批次 B，两位标注员，同一批 100 条）**

| 指标 | 值 |
|---|---|
| 完全一致 | 88/100（88.0%） |
| Cohen's kappa（未加权） | 0.548 |
| Cohen's kappa（二次加权） | 0.673 |
| 两人都判对 | 97.0% |
| 自动 contain | 97.0% |

分歧 12 条，其中 **10 条是「3 分 vs 2 分」**（完整 vs 部分正确），另有 2 条涉及 1 分。
也就是说：标注员对「明显错」判断一致，分歧集中在「算不算完整」。

未加权 kappa 只有 0.548，是因为分数分布极度偏斜（80 条给了 3 分），
高度偏斜会把 kappa 压低；二次加权 kappa 0.673 属于「实质性一致」。
两人对正确率的判断与自动 contain 完全重合（都是 97%），
说明**在这批数据上自动指标已经能替代人工做粗筛**。

改进项：评分指南里「完整」这条要写更细（缺一个限定条件算不算 2 分），
否则标注员会稳定地在 2/3 边界上分歧。

### 4.10 改写门控：只在没把握时才花钱

4.8 的改写是「每条都改」，成本与延迟翻倍。按 CRAG 的思路加一个零成本评估器：
先做一次原始检索，计算 top1 与 top2 的相对分数间隔，
间隔小于阈值（0.25）才触发改写。500 条实测（句级索引，300 token 预算）：

| 策略 | Recall | 改写次数 | 改写比例 | 平均延迟 |
|---|---|---|---|---|
| off（不改写） | 0.912 | 0 | 0% | 1 ms |
| always（全改） | **0.966** | 500 | 100% | 990 ms |
| auto（门控 0.25） | 0.948 | **190** | **38%** | 379 ms |

**门控用 38% 的改写拿到了 67% 的收益**（(0.948−0.912)/(0.966−0.912)）。
在“召回–成本”平面上，自动门控严格优于两端：比不改写多 3.6pt 召回，
比全改写省 62% 的调用与 62% 的延迟。

与 4.8 端到端结果对照：全改写把 contain 从 0.915 提到 0.985，
门控预期落在两者之间（约 0.96），且只对 38% 的请求付出额外延迟——这是默认推荐配置。

复现：`python scripts/rewrite_gate.py --tokens 300`；开关 `RAG_REWRITE=auto`。

### 4.11 没有 embedding 时：用对话模型做重排

DeepSeek 的 API **不提供 embedding**（`/v1/embeddings` 返回 404，模型列表只有
`deepseek-flash` 与 `deepseek-v4-pro`）。作为替代，我们让对话模型给候选片段打相关性分
（0–10），再按分数排序，观察在**固定 token 预算**下能否替代向量检索。

| 设置 | BM25 原始顺序 | LLM 重排 | 差值 |
|---|---|---|---|
| 候选 8、预算 300 tok（n=100） | 0.9200 | 0.9200 | **+0.0000** |
| 候选 30、预算 150 tok（n=50） | 0.9000 | 0.9200 | +0.0200 |
| 候选 30、预算 150 tok（n=200） | 0.8700 | **0.9250** | **+0.0550** |

**两个观察：**

1. **重排只在预算截断时有用。** 候选 8 条、预算 300 token 时全部候选都塞得下，
   排序变了但集合没变，召回一模一样——这说明「重排提升召回」这个说法有前提条件。
2. **预算紧、候选池大时，重排能补回不少。** 150 token 只够放 10 条左右，
   从 30 条里挑哪 10 条就变得关键，重排带来 +5.5pt。

代价是每条查询多一次模型调用（约 0.0025 元、0.7 秒），比 embedding 贵得多。
结论：**重排可以当作「没有向量检索时的补丁」，但不能替代 embedding**——
它不改变候选池，只是换个顺序。

## 5 讨论

**5.1 级联在改写集上位于前沿。**
0.970 与深检索的 0.975 相差 0.5 个百分点，但成本只有 47%。
在原始问句集上，级联与深检索同为 0.980，成本只有 33%——不过此时 naive top-3 也能做到 0.980，
说明该集合的区分度不足。

**5.2 负结果：合成集饱和。**
两个集合上，除 `fixed-bm25-k1` 外的所有策略，Recall 差异都落在置信区间内。
原因很直接：问题由同一批句子生成，词汇高度重合，BM25 几乎总能命中。
这提示我们后续必须换真实数据集，否则任何「策略更优」的结论都不可信。

**5.3 预算路由的局限。**
`adaptive-budget` 在预算宽裕时等价于全量深检索，因此成本和 `fixed-hybrid-k5` 几乎一致。
全局预算只控制「平均花多少」，控制不了「哪里该多花」——这正是级联要解决的问题。

## 6 局限

1. 语料与问题均为合成，存在同源偏差，指标绝对值不可外推
2. embedding 为离线哈希占位，尚未接入真实语义模型
3. 成本按固定单价粗估，未接入真实计费账单
4. 单机 CPU 评测，延迟数字不代表生产环境
5. 只测了 Recall/EM/F1，未做人工偏好或答案忠实度评估

结论：当前瓶颈在**检索**，不在生成；下一步应优先做查询改写或更大的 k，而不是继续调提示词。

### 4.5 分块粒度实验（负结果）

把语料按句子切块（每条事实一块）后，Recall@3 从 0.946 降到 0.832（k=3）、0.878（k=8）：
块越小，同等 k 下覆盖的文字越少，而 Recall@k 是「召回上下文里是否出现答案句」，
对大块天然有利。这说明**该指标会偏爱大分块**，跨粒度比较必须在**相同 token 预算**下重做。
