# 多维预算：第二个维度为什么不咬合

> 问题：真实系统同时受 token、延迟、钱约束。二维预算会不会改变最优策略？
> 结论先行：**在本工作所处的设定里，第二个维度不咬合，预算退化成一维 token。**

## 一、两个维度的量级

| 环节 | 耗时 | 说明 |
|---|---|---|
| BM25 检索 | 16 ms | 无向量化 |
| 向量检索（bge-m3 / bge-large） | 42 ms | 含查询编码 |
| 混合检索 | 69 ms | 两路 + 融合 |
| 自适应混合 | 70 ms | 与混合相同 |
| **生成（强档）** | **898 ms** | p50，见 6.8 |
| 生成（强档 + 改写） | 1765 ms | 改写占一半以上 |

**检索侧最大 70 ms，生成侧最小 898 ms → 检索最多占端到端 7.2%。**

## 二、三条共线性

1. **token ↔ 钱**：单价固定，钱 = token × 常数，完全共线。
2. **token ↔ 生成延迟**：prefill 与上下文长度近线性，也基本共线。
3. **检索延迟 ↔ token**：不同检索器的延迟差只有 16–70 ms，选哪个对延迟预算几乎没有影响。

所以「二维预算」在数学上仍然是一个一维问题：**约束 token 就够了**。

## 三、唯一有非共线成本的动作：查询改写

| 动作 | token | 延迟 | 召回增益 |
|---|---|---|---|
| 强档检索 | 318 | 898 ms | 0.937 |
| 强档 + 改写（全量） | 约 320 | 1765 ms | 0.900（下降） |
| 强档 + 门控改写 | 约 317 | 1788 ms | 0.902（下降） |

改写**同时**增加延迟、增加 token，且在这批题上**不带来召回增益**——所以它在任何二维预算下都不划算。
这正是「多维预算」唯一可能发挥作用的地方，而数据说它不划算。

## 四、什么时候二维才真正咬合

| 场景 | 为什么 |
|---|---|
| 网页检索（按次收费） | 每次调用固定费用，与 token 无关 → 成本向量不同 |
| 多模型路由（大模型贵但更准） | 钱换质量，与 token 不同维度 |
| 严格延迟 SLA（< 200 ms 端到端） | 改写直接被排除，策略改变 |
| 流式场景（首字延迟优先） | 延迟与 token 的关系被摊薄 |

**本文的设定不属于以上任何一种**，因此一维预算是正确选择，而不是简化。

## 五、这对论文的意义

这是一个**否定性但有价值**的结论：

> 不是所有系统都需要多维预算。当检索延迟远小于生成、单价固定时，多维预算退化为一维；
> 只有存在「固定调用费」「多模型选择」或「严格 SLA」时，二维才咬合。

写进论文有两个好处：
1. 解释了我们为什么只用标量预算（防御「为什么不建模延迟」的质疑）
2. 给后续工作一个清晰的适用边界
